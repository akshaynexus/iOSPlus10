## 3. Does 0126 fix a bug we hit? Yes [V for the mechanism, I for the exact event]

- What it changes: `flush_dcache((vm_offset_t)(pp << PAGE_SHIFT), PAGE_SIZE, TRUE)` shifted the 32-bit
  `ppnum_t` in 32 bits. All negroni RAM is above 4 GiB (starts at 0x841004000), so every call flushed a
  wrong physical address and `phystokv_range` panicked. The fix casts to `pmap_paddr_t` first.
- slop's proof (slop NOTES.md:919-921): the 0128 trace showed
  `IOGeneralMemoryDescriptor::memoryReferenceCreate -> mach_make_memory_entry_internal ->
  vm_object_change_wimg_mode -> pmap_set_cache_attributes -> pmap_sync_page_attributes_phys ->
  flush_dcache -> phystokv_range`; after 0126, gl_test ran on the GPU with no panic past 4 min.
- Our record: `patches/xnu/README-gpu-kernel.md:28`: slop 0119 boot, panic `phystokv_range` illegal
  PA **0xc7a24000**. That is 0x8c7a24000 with the top bits cut off [I: the same truncation].
  README-gpu-kernel.md:36-42 guessed "write-combined view of XNU memory"; that guess was the trigger,
  the truncation is the bug.
- Our 0230 removed the trigger, not the bug: no write-combined mapping of XNU-managed memory
  (client surfaces map copyback, NegroniSurface.cpp:846,921 in the patched tree; WC only for
  physical-address descriptors: NegroniSurface.cpp:382-383, NegroniGPU.cpp:935 pool only).
  Other callers still reach the bug: `osfmk/vm/vm_fault.c:1722,5276` (decompressed page of an object
  with non-default WIMG) and `osfmk/vm/vm_pageout.c:9774` (`UPL_REQUEST_FORCE_COHERENCY`).
- Our shipping kernel has the bug [V]: `_pmap_sync_page_attributes_phys` in `out/kernel/kernel.macho`
  starts with `lsl w0, w0, #14` (32-bit); with 0126 it is `ubfiz x0, x0, #14, #32` (section 7).
- Conclusion: take 0126. It is a latent panic for any future WC/inhibit-cache mapping of managed memory
  (Metal, IOSurface cache modes).
