# Review: patch 0261 (Wi-Fi stage 1, MHI firmware download), 2026-10-25

Scope: `patches/xnu/0261-negroni-wlan-mhi-fw.patch` (tree `out/kernel/wt-wlan4`):
`bsd/dev/negroni_wlan.{c,h}`, `negroni_wlan_mhi.{c,h}`, `negroni_wlan_bhi.c`, the hand-over in
`negroni_wifi.c`, `negroni_ufs_wlan_area_read` in `negroni_ufs.c`, and `scripts/wifi/mkwlanarea.py`.
References: OnePlus kernel `out/src/op-kernel` (e9da592) `drivers/bus/mhi/host/{boot,init,main,pm}.c`,
`internal.h`, `drivers/net/wireless/cnss2/pci.c`; this XNU tree (`osfmk/vm`, `osfmk/arm`).

Marks: **[V]** checked in source (file:line given) or by a build/run on the host. **[I]** inference.
Nothing in this review ran on the phone. The chip has never answered on PCIe in this port.

## Summary

The original patch could panic the kernel on its most likely path (an empty firmware area). It
put BAR0 at an address the chip cannot decode. It wrote 64-bit doorbells in the wrong order for
RAM above 4 GiB. Its MHI order (M0 after AMSS) differs from Linux. All of these are fixed in
the tree and the patch is regenerated. The default boot-args do not start the driver.

## Findings and fixes

### Critical (kernel panic or memory corruption)

1. **`ml_io_unmap` of an `ml_io_map` mapping panics.** [V] `ml_io_map` -> `io_map(..., unmappable=false)`
   allocates in `io_submap` with `KMA_PERMANENT` (`osfmk/arm/io_map.c:120-130`). `ml_io_unmap` calls
   `kmem_free(kernel_map, ...)` (`osfmk/arm64/machine_routines.c:1591-1595`). `kernel_map` holds
   `io_submap` as a permanent entry (`io_map.c:76-78`, `KMS_PERMANENT`), and `vm_map_delete` panics
   on a permanent entry in a kernel pmap map (`osfmk/vm/vm_map.c:8182-8189`). `wlan_cleanup` ran this on
   every failure after the pool mapping, for example "no firmware area header", which is the
   state of every phone today (the area is not written).
   **Fix:** the second view uses `ml_io_map_unmappable(pa, size, VM_WIMG_WCOMB)` (kernel_map,
   not permanent; `machine_routines.c:1574-1580`), which `ml_io_unmap` can remove.
   Also: VM_WIMG_IO (Device nGnRnE) on DRAM is the type XNU itself refuses on managed pages
   (`pmap.c:10647-10660`); Normal non-cacheable is the correct type for rings. The poller now has
   a `dmb ld` between the context rp read and the element reads.
   **Not fixed (other driver):** `bsd/dev/negroni_adsp.c:742` calls `ml_io_unmap` on an
   `ml_io_map_wcomb` mapping. Same panic. It runs only with `negroniadsp=1`.
2. **BAR0 was not aligned to its size.** [V] The patch wrote 0x60300000 to BAR0. A BAR decodes
   only a naturally aligned range; 0x60300000 is not 2 MiB aligned, so the low bits read back as 0
   and the chip decodes 0x60200000-0x603fffff [V PCI rule]. CPU access to 0x60300000 then reaches BAR
   offset 0x100000, not the MHI registers. The BAR size is 2 MiB on WCN6855 [I: no lspci from this
   phone]. **Fix:** size probe with decode off, base = first size-aligned address in the window
   (0x60400000 for 2 MiB, the same choice the Linux PCI core makes), read-back check, refuse an I/O
   BAR or a BAR that does not fit. The map length is the BAR size (max 2 MiB).
3. **Offsets from the chip were used without a check.** [V] `BHIOFF`, `BHIEOFF`, `CHDBOFF` and
   `ERDBOFF` were added to the BAR0 base without a check. A dead link reads 0xffffffff, so the
   next access was at BAR0 + 4 GiB, outside the mapping: a data abort panic.
   **Fix:** each offset is checked against the mapped length (Linux does the same for CHDBOFF/ERDBOFF,
   `init.c:515-519`). `negroni_wlan_rd/wr` also refuse any offset outside BAR0 (read gives
   0xffffffff). Every wait loop treats 0xffffffff as "link down" and stops.
4. **DMA memory was freed while the chip could still use it.** [V] On failure the pool was freed with
   bus master on, after the chip had the context, ring, firmware and vector addresses. A late
   device write would land in reused pages. **Fix:** `wlan_quiesce` drops device wake, sets
   MHICTRL RESET, turns off bus master (PCIe BME), reads the command register back, waits 10 ms,
   and only then frees the pool. `flush_dcache64` runs before `kmem_free`, so the next owner of the
   pages gets no stale lines from the cacheable view.
5. **A SHA-256 mismatch was only logged.** [V] `wlan_load` printed "MISMATCH" and returned 0, so a
   corrupt image went to the chip. **Fix:** stop with `EBADMSG`.

### High (the chip would not reach mission mode)

6. **64-bit doorbell write order.** [V] Linux writes the high word, then the low word; the low
   write triggers the doorbell (`main.c:84-89` `mhi_write_db`; `init.c` `mhi_init_mmio` reg_info:
   `*_HIGHER` before `*_LOWER`). The patch wrote low, then high. All XNU RAM is at 0x8_4000_0000 or
   higher, so the first doorbell would carry a stale high word. **Fix:** `mhi_write64` (high, low)
   for all doorbells and base registers.
7. **MHI order differed from Linux (coordinator question).** [V] Linux order:
   BHI SBL (`boot.c:493-511`) -> MHICTRL RESET clear + MHISTATUS READY (`pm.c:205-222`) ->
   `mhi_init_mmio` (`pm.c:243`) -> event-ring elements + doorbells (`pm.c:250`, `mhi_setup_event_rings`
   `pm.c:154-185`) -> MHICTRL M0 (`pm.c:253`) -> EE event SBL (`main.c:940-950`) ->
   `DEV_ST_TRANSITION_SBL` -> `mhi_download_amss_image` (BHIe) (`pm.c:767-781`, `boot.c:566-585`) ->
   EE AMSS -> mission mode (`pm.c` `mhi_pm_mission_mode_transition`) -> channels.
   - The author's claim "MMIO context setup after the SBL download" is **partly right**: Linux
     programs MMIO after the SBL download, but only after MHICTRL RESET clears and MHISTATUS READY is
     set. The patch did it after BHI_EXECENV == SBL, without the READY wait.
   - The author's claim "M0 after AMSS should still work" is **wrong as a match to Linux**: Linux
     requests M0 right after READY, before BHIe. The AMSS download starts when the SBL EE event
     arrives on the control event ring. [I] The SBL may also wait for M0 before it accepts BHIe.
   **Fix:** the sequence now follows Linux (see README-wifi.md "Sequence"). The SBL wait accepts
   the EE event or BHI_EXECENV.
8. **Event rings were not given to the device correctly.** [V] The doorbell was rung after the M0
   request, and the context `wp` in host memory stayed at the ring base (Linux sets
   `*ctxt_wp = base + len - el_size` before the doorbell, `pm.c:177-181`). **Fix:** both, before M0.
9. **No device-wake doorbell.** [V] Linux clears the wake doorbell (channel doorbell 127) in
   `mhi_init_mmio` (`init.c:521-525`) and asserts it on M0 (`pm.c:283` `wake_get`, default
   `mhi_assert_dev_wake` `pm.c:1026-1045, 1108`; cnss2 sets no own wake_get). Without wake the chip
   may enter M1/M2. **Fix:** clear in init, set to 1 after M0, clear on failure.
10. **MHICFG NHWER kept the device value.** [V] Linux writes NER = total rings and NHWER = hardware
    rings (`init.c` reg_info). **Fix:** NER 2, NHWER 0 (ath11k has no hardware event rings).
11. **Channel context array too short.** [V] Only 34 entries fit before the event contexts; Linux
    allocates `max_chan` entries (128 for ath11k). **Fix:** a full 128-entry array (5632 B); the
    rings moved; `_Static_assert`s check the layout.

### Medium

12. Default time-out 2000 ms per wait; cnss2 uses 10 s (`cnss2/pci.c:219`), ath11k 20 s [V].
    **Fix:** default 10000 ms (still on its own thread; boot does not wait).
13. No execution-environment check before BHI [V]. **Fix:** stop unless EE = PBL and no SYSERR (Linux
    takes the BHI path only for `MHI_IN_PBL`, `pm.c:759-766`, `pm.c:1130-1168`).
14. The command register write was a 32-bit read-modify-write; it wrote the RW1C status bits back
    [V PCI rule]. **Fix:** the upper 16 bits are written as 0.
15. A START_CHAN time-out was reported as "completion code 0xff". **Fix:** its own line.
16. BHI error logging: only ERRCODE. **Fix:** ERRCODE + ERRDBG1..3 (`boot.c:247-311` `mhi_fw_load_bhi`).
    `BHI_INTVEC` = 0 before BHI, as Linux power-up does (`pm.c:1123,1163`).
17. `mkwlanarea.py` did not require `m3.bin`, and its docstring said ~12 MiB (it is ~22 MiB).
    **Fix:** both.

## Checked and correct [V]

- MHI, BHI and BHIe register offsets and fields: `internal.h:15-205`.
- Context layouts (44 bytes, packed) `internal.h:212-250`; `bhi_vec_entry {u64 addr; u64 size}`
  `internal.h:266-269`; ring element format; START_CHAN dword1 `internal.h:297-300`; event fields
  `internal.h:306-321`; EE/state values `include/linux/mhi.h:133-167`; `MHI_EV_CC_SUCCESS` = 1.
- BHIe vector: one entry per 512 KiB segment, the last holds the rest; TXVECSIZE = 16 x data
  segments (the vector table is the extra last buffer, `boot.c:338-402, 404-429`). 5287936 B ->
  11 entries, 5609392 B -> 11 entries; FW_CAP 6 MiB -> at most 12.
- SBL size = min(512 KiB, file size) (`boot.c:493-497`). One buffer serves BHI and BHIe (same bytes).
- Firmware choice: SoC version at BAR0 + 0x224 (`init.c:978-990`), lower 4 bits of major == 2 ->
  `amss20.bin`, else `amss.bin` (`cnss2/pci.c:5109-5119, 5134-5150`).
- Ring alignment: each ring base is aligned to its size (Linux `mhi_alloc_aligned_ring`).
- DMA: one contiguous pool; physical addresses from `pmap_find_phys`; now checked against the
  36-bit mask (`cnss2/pci.c:4483-4487`). The firmware is written through the cacheable view and
  pushed to RAM with `flush_dcache64`; rings and contexts use the non-cacheable view.
- Area format: kernel `struct wlan_area_entry` = 88 bytes = Python `<48sII32s`; header 16 + 256 x 88
  = 22544 B <= 32 KiB (now `_Static_assert`ed). Test run of `mkwlanarea.py` on `out/firmware/wlan`:
  198 files, 23146496 of 33554432 bytes; amss.bin at 0x8000, amss20.bin at 0x562000, m3.bin at
  0x15cb000, all 4 KiB aligned, SHA-256 match when parsed by the kernel rules (test image deleted).
- Block map: kernel base = N - 1025 - 2048 - 8192 - 8192 = N - 19457, same as the dd recipe.
- Boot-args: `negroniwlan` default 0; `config/negroni-ne2211.toml` has `negroniwifi=4` and no
  `negroniwlan`, so neither the survey write steps nor the driver run by default. `negroniwlan=2`
  starts the driver only when steps 1-10 all passed; the probe menu wins over the boot-arg.
- Every wait in the driver is bounded by `negroniwlan_to`.

## Still open

- [I] **SMMU.** PCIe0 SID 0x1c01 sits behind the apps SMMU with `qcom,handoff-smrs`. If no
  SMR/S2CR matches 0x1c01 and sCR0.USFCFG = 1, every chip DMA faults. The expected symptom is
  "BHI SBL error/timed out" (a safe stop). This needs a bypass S2CR or a context bank.
- [I] **Reads over a dead link.** The driver handles 0xffffffff. On some Qualcomm setups a
  completion time-out raises an SError instead (a panic). Software here cannot prevent that.
- [I] The root-port bridge memory window (type-1 header 0x20) is not programmed (the Linux PCI core
  does it). The DWC outbound path uses the iATU, so this is probably not needed.
- [I] ath11k does a SoC global reset, L1SS fix and MHICTRL reset before power-up
  (`ath11k_pci_sw_reset`). Stage 1 relies on the fresh power-on from survey steps 5-8.
- [I] After success nobody polls the event rings; they can fill. Stage 2 must keep polling.
- [I] MHI CTRL/DATA window = the pool only. Stage 2 (QRTR buffers, QMI `respond_mem`) must widen it.
- [I] The cacheable and non-cacheable views of the pool exist at the same time (as Linux arm64
  `dma_alloc_coherent` does for non-coherent devices). No CPU write goes through the cacheable
  view after the firmware flush.
- Survey steps 5-8 (0260) run synchronously in the UFS init path when `negroniwlan` >= 1; their
  waits are bounded (`wait_for`, 100 x 10 ms link loop). They have never run on a phone.
- `negroni_adsp.c:742` `ml_io_unmap` panic (finding 1), not in this patch.

## What the first phone test must show

Boot with `negroniwlan=2` only after the owner approves (survey steps 5-8 write GCC/TLMM/PCIe and
power the chip). Expected `NEGRONI WLAN:` lines in order: BAR0 at 0x60400000 with REGLEN/VER not
0xffffffff; a SoC version and the firmware name; the DMA pool; "firmware area has 198 files" (after
the area is written); both files "sha-256 OK"; EE 0 and MHISTATUS before BHI; BHI SBL; MHISTATUS
READY; MHI ctx; M0; EE SBL; BHIe 11 segments; EE AMSS; channels 20 and 21 started; "stage 1 done".
On any stop: the "MHI reset requested and bus master off" line, then "stage 1 stopped", and the
boot continues. Without the area written, the run must stop at "no firmware area header" and boot
must continue (this checks finding 1 on the phone).
