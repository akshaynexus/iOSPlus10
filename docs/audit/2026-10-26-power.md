# Power audit 2026-10-26: battery, charger, thermal, CPU, power off, USB

Scope: patches/xnu 0270-0274, 0276 (battery/charger), 0280 (thermal), 0284 (CPU governor), 0211/0213/0214
(power off, reboot mode, PS_HOLD), 0282 (USB reset); README-battery.md, README-reboot.md, README-thermal.md,
README-cpufreq.md, docs/charger-glink-plan.md, docs/notes.md "Battery" and section 22. 0275 (display-off-fast)
is out of scope. Originals: out/src/op-kernel (Qualcomm/OnePlus kernel), out/src/op-modules (OPLUS charger),
out/live.dts, out/kernel/xnu (base XNU).

Marks: **[V]** = read in the source, the DT, a log or a build. **[I]** = inference. Nothing here was run on the
phone or built by this audit. Read-only.

Summary in one line: the reads are solid and verified; charging and the percentage still depend on the untested
GLINK path (0274); thermal and CPU control are coarse and have no counterpart to Android's trip points; the cores
only ever WFI; power off is fixed in code but not tested.

## 2. Deviations that can bite

1. **No cpuidle.** Every core spins WFI between tasks [V cpu.c:570-591]. Android collapses cores and clusters.
   This is the largest standing idle load that we control and the main reason "~1 A at 5 V covers only the idle
   load" [V notes.md handoff]. The governor (0284) cannot fix it: d1/d2 stay at their top rows [V README-cpufreq.md].
2. **ABL-row floor.** 0284 and 0280 never go below the ABL row (0098 rule) [V 0284:119-122]. Boot 0097 ran d1 row 15
   and d2 row 14 without a fault [V README-cpufreq.md "Before 0284"]. The rule blocks the two hottest clusters.
3. **Thermal threshold 70 C on the hottest of 32 sensors** [V 0280:243]. The DT CPU zones act at 110 C (pause) and
   the GPU at 95 C [V live.dts:8017-8462]; the OPLUS IPA zone acts at 53 C with cpufreq cooling [V :10260-10311].
   So 0280 caps the GPU and CPU early (modem/aoss/nspss sensors also count toward `max`) and never pauses a core.
   `strncmp(name, "cpu", 3)` also matches `cpuss-*` [V 0280:229]: intended, but the log "cpu" value mixes both.
4. **No BCL reaction.** Android drops modem, CDSP, GPU and pauses cpu5 at pm8350b-bcl-lvl0/1/2 [V live.dts:9602-9764]
   and limits ibat at 9000/10000 mA [V :9570-9601]. We read the BCL only. A brown-out at low SoC is the phone's
   answer [V plan.md: brown-out at 16 %].
5. **RPMh votes are ACTIVE-TCS only and never released**: the BT rails (`0330:49` "never voted off"), the Wi-Fi
   rails (slop 0122, apps DRV2 ACTIVE TCS [V :19-21]); the ADSP proxy votes are dropped at handover [V 0240:47].
   With no AP sleep this costs only the rails that stay on after a failed bring-up [I]. No SLEEP/WAKE TCS content
   exists, so a future AP sleep would keep every vote [V grep: no SLEEP/WAKE writes].
6. **OCV table is generic** (4.45 V class, 23 points) [V 0271:155-159]; the DT vfloat is 4435 mV [V live.dts:6683].
   Near 10 % the table error is about +-3 % [I README-battery.md s.10]. Current steps are 78 mA on the BCL [V],
   so the coulomb term is coarse.
7. **Mean-cell voltage, 1S assumptions.** VBAT is on the 1S side (`mid2s` = `vbat`) [V phone log]; 5000 mAh 1S
   equivalent is assumed for the coulomb count [I 0271 README s.3].
8. **GLINK writes assume OPLUS ids under `OPLUS_FEATURE_CHG_BASIC`**: BATT_CHG_EN 24, USB_SUSPEND_PMIC 26,
   USB_IN_STATUS 47 [V oplus_battery_sm8450.h enum positions]. The stock firmware build defines it [I]. The
   one-time property dump of 0274 checks this [V README s.9].
9. **No FV/FCC/JEITA from us** (0274 writes three ids) [V 0274:215-225]. On Android the HLOS loop sets FV/FCC
   every 5 s [V oplus_charger.c:110,7556-7558]. If the PD's defaults are conservative, charging is slow; if the PD
   expects the HLOS loop, it may not charge at all or may stop on its own timer [I].
10. **0272/0273 are dead code paths on this phone** (no APID, fuse off) [V README s.8-9]. They stay in the build,
    and 0273 still votes the AOSS QDSS clock (`{class: clock, res: qdss, val: 1}` [V qcom_aoss.c:286-288]) when
    `negronichg_arb=auto` falls to the debug route without `negroniadsp` [V README s.8]. That vote is never released.
11. **BCL MONITOR_EN is never written** [V 0271 README s.3]; the values exist only because XBL/ABL left the monitor
    on [V phone logs]. A boot where it is off shows the static 100 %.
12. **Power off with USB in**: PON trigger `USB_CHARGER` reboots the phone after SHUTDOWN [I notes.md 22]. 0214
    cannot stop this; the PON log at the next boot shows it.
13. **0280 votes are not restored after a thermal cap** until the sensor drops below 60 C [V 0280:255-265]: a
    hysteresis band of 10 C with 10 s steps; a boot burst at 80 C [V handoff] pulls both caps two steps down
    (GPU 12 -> 10, CPU 3200 -> 1800) before the UI is up [I].

## 3. What remains, ordered by value for "charges, runs cool, honest %"

1. **Boot 0274 (GLINK) and read the property dump** [V plan.md "Next" item 2]. This decides charging and the
   percentage at once: `READY`, `input limit read back: 1500 mA`, `ibat` > +500 mA, `soc src=glink`.
   If READY never comes: `negroniadsp_step=10` (servreg locator) [V charger-glink-plan.md s.5].
2. **Add FV/FCC over GLINK** after 1 works: `VOLTAGE_MAX` (= 4435 mV from the DT) and `BATT_CHG_CTRL_LIM` with the
   DT JEITA bands [V oplus_battery_sm8450.c:8194-8219; live.dts:6678-6700], read-back each cycle. Without it the
   PD's defaults decide the charge curve [I].
3. **cpuidle**: PSCI `CPU_SUSPEND` from `cpu_idle()` with the lowest per-core state first (the DT `qcom,lpm` /
   psci idle-states of live.dts: not read in this audit [I]). This is the largest idle-power item we own.
   Needs the timer and IPI wake path checked (XNU expects WFI to return on an IRQ; a PSCI suspend returns through
   the reset vector) [I].
4. **Drop the ABL-row floor for d1/d2** (owner decision, evidence boot 0097) [V README-cpufreq.md "Floor"]. Then
   the governor can idle the big cores at their lowest rows.
5. **Thermal parity**: per-zone thresholds in 0280 (CPU 110 C pause -> we have no pause: use the lowest row;
   GPU 95 C; IPA 53 C cpufreq cooling) and a BCL level reaction (read `INT_RT_STS` of 0x4710 in the 1 s loop:
   already allowed [V 0270:307]) [I design].
6. **Persist `fSoc`** across boots (as the RTC offset file) so the first value is not the boot-load value
   [V README s.10 "Nothing is kept across boots"].
7. **Battery temperature**: `BATT_TEMP` from GLINK into `Temperature` (0274 reads id 12 [V 0274:216]; 0276 does
   not publish it [I: not seen in 0276 grep]) so iOS thermal/charging logic sees the cell.
8. **Release votes**: the QDSS vote of 0273 and the Wi-Fi/BT rails after a failed bring-up [V 0330:49].
9. **Power-off test** (0214) and the PON log read [V notes.md 22]: cheap, one boot.

## 4. Risks for the queued tests (plan.md "Next")

- **Charger test (out/ios16-chg3)**: needs `negroniadsp=1` (ADSP boot: SoC-reset risk, firmware area on userdata)
  [V README s.9 Risks]. 0274 writes only after READY; a lost cycle clears READY [V]. The ramp is 5 tries per plug,
  up to 2000 mA [V 0274:228-230]; a bad adapter drops VBUS and the back-off steps down at 4500/4550 mV [V].
  Watch: `glink: ... ret_code` non-zero on id 24/26/47 = wrong enum (then only ICL works).
- **Battery below 20 % at boot**: the boot load (-1.2 A) with ~1 A input [V log 13:32] can brown out as before
  [V plan.md 16 %]. Charge in fastbootd first [V handoff].
- **Thermal/CPU images (ios16-pwr, ios16-cpugov)**: `negronithermal=0` and `negronicpufreq_gov=0` are the
  fallbacks [V READMEs]. 0280's first 10 s step may cap the GPU during the 80 C boot burst [I]; check the
  `[step]` lines against `gxclk`.
- **0214 power-off test**: a wrong PON type leaves the phone in a reset loop only if the type write fails half way;
  0214 re-enables CTL2 even after a failed type write [V 0214:220-224]. With USB in, expect a USB_CHARGER auto-boot
  [I notes.md 22].
- **0282**: no risk seen; `negroniusb_resetdrop=0` restores the old path [V 0282:8,44].

### RPMh votes of Wi-Fi and Bluetooth after a failed stage (finding, no edit)

- [V out/kernel/tree-pwr bsd/dev/negroni_wifi.c:376-392] `step_chip_on()` votes five rails in order (smpe2 1012,
  smpb11 966, smpb10 1800, smpc1 1900, smpb12 1350 mV) through `negroni_rpmh_wifi_enable()` (negroni_rpmh.c:400,
  `rh_vreg_enable(res, mv, -1)`: ACTIVE TCS of the apps DRV2). A failed vote returns false at once: the rails voted

- [V negroni_rpmh.c:389-398] The only "off" entry points are `negroni_rpmh_vreg_disable()` (ldoc11 only, 0350) and
  `negroni_rpmh_cam_rail(..., on=false)` (camera); no off entry exists for the Wi-Fi or BT rails.
- [V negroni_bt.c:31, :774-778, :812-814] Bluetooth votes smpb11 966, smpc1 1900, smpb12 1350, ldoe7 2800 mV; on a
  failure only the GCC branch vote is restored and BT_EN goes low; the comment says the four rails are never voted
  off (all shared; smpb12 is the UFS vccq parent).

  voted off. Only smpe2 and smpb10 (Wi-Fi only) and ldoe7 (BT only) are candidates, and only with a reference
  count across Wi-Fi and BT (a BT failure must not drop a rail that a running Wi-Fi needs, and the reverse).
- [I] Proposal for the owners of negroni_wifi.c / negroni_bt.c / negroni_rpmh.c: an off entry
  `negroni_rpmh_radio_rail(res, on)` with a per-rail count (Wi-Fi and BT holders), called on the failure paths of
  `step_chip_on()` (the rails voted so far) and of the BT step 3+; smpb12 excluded. Value: small while the AP never
  sleeps (RPMh aggregates with the other DRVs; the PMIC keeps a rail on while any master votes it), larger once an AP
  sleep exists (no SLEEP/WAKE TCS content is written today, audit item 5).
