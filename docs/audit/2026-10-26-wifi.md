# Wi-Fi audit 2026-10-26: patches 0260-0266 against cnss2, Linux MHI and ath11k

Scope: `patches/xnu/0260`..`0266` (PCIe inventory, MHI firmware, power-up, levels 2-4, IPCR rings, QRTR,
QMI WLFW), `patches/xnu/README-wifi.md`, `docs/wifi-plan.md`, `docs/notes.md` section 16, `scripts/wifi/*`.
Originals: `out/src/op-kernel/drivers/net/wireless/cnss2` (pci.c, main.c, qmi.c, power.c, pci_qcom.c),
`out/src/op-kernel/drivers/bus/mhi/host` (pm.c, boot.c, init.c, internal.h), `out/src/wlan-linux/drivers/net/
wireless/ath/ath11k` (core.c, pci.c, pcic.c, mhi.c, qmi.c, ce.c, htc.c, wmi.c, mac.c, dp*.c, hal*.c),
`out/live.dts`, `out/firmware/wlan`. The reference iOS ports `external/ios-sailfish` and `external/ios-spes`.

Not present: the Qualcomm host driver (qcacld-3.0 / qca-wifi-host-cmn) is not in `out/src` [V: `find out/src
-iname 'qcacld*'` finds nothing; `out/src/wlan-cnss` holds only cnss2, cnss_utils and icnss2]. The OnePlus kernel
tree only has the cnss2 platform driver; the WLAN host driver is an out-of-tree module that is not checked out.
ath11k (WCN6855 hw2.x, the same MHI/QMI/CE/HAL family as QCA6490 hsp) is the reference used here.

Method: the patched kernel trees (`out/kernel/tree-wlan7`, `wt-wlan4`) are deleted, so the driver sources were
rebuilt in a scratch directory by applying 0261, 0263, 0264, 0265, 0266 in order (`patch -p1`). Line numbers of
`negroni_wlan*.c/h` below are of those rebuilt files (= the tree after 0266). Lines of 0260 / 0262 are patch lines.

Marks: **[V]** = read in the source, the DT, a log or a build. **[I]** = inference. Nothing was built, run or
flashed by this audit. Read-only except this file.

Summary in one line: the host side of the chip boot (PCIe link, MHI, firmware download, QRTR, QMI WLFW up to
FW_INIT_DONE) is written and follows cnss2/Linux closely, only the PCIe link part has run on the phone [V], the
firmware area is not written to the phone yet [V], every chip DMA address is above 4 GiB (Android and Linux never
give this firmware such addresses) [V], and about 80 % of the lines needed for "scan + connect + IP" (CE/HAL,
HTC/WMI, HTT/DP, the STA state machine with WPA2, the iOS en0/Apple80211 glue) are still to write.

## 0. Corrections to the current docs

- The brief says "no reference port has Wi-Fi". **Wrong** [V]: `external/ios-sailfish/README.md:17,32` says the
  Settings page scans, joins WPA2, gets DHCP and Safari loads pages (QCA6174, ath10k-class); patches
  `0169`-`0175`, `0178`, `0179`, `0181` (6342 patch lines) hold the whole stack including the iOS side.
  `external/ios-spes` (WCN6750, ath11k-class firmware over QRTR) has WLFW + CE + HTC + WMI + passive scan in
  `0099-spes-modem-wifi.patch` (6374 lines, header at :3049-3058 and :3474-3482) and an en0 + Apple80211 design in
  `0113-spes-wifi-en0-apple80211.patch` (2326 lines, :151-177), the latter "not ported yet" per its README:22,57.
  Both are design references only (no license file).
- README-wifi.md "no bit 1 (no qcom,drv-supported in live.dts:13840)": cnss2 reads `qcom,drv-supported` from the
  **PCIe controller node**, not the wlan node (`pci_qcom.c:157-168`: `root_of_node->parent`), and
  `out/live.dts:20821` (pcie0) has it. So the Android HOST_CAP `feature_list` carries the DRV bit too; 0266 sends
  0x5 (`negroni_wlfw_tables.h:46`). Effect on the firmware: unknown [I]; DRV = PCIe drive-strength/L1ss power
  feature; without it the firmware should not expect DRV [I].
- README-wifi.md "Linux never writes M0 on M1; it toggles DEVICE_WAKE": Linux writes **MHISTATE M2**
  (`pm.c:341-343` `mhi_set_mhi_state(MHI_STATE_M2)`) and then, with dev_wake held, does wake_get + wake_put
  (`pm.c:352-359`). 0263 writes no M2 and writes wake 0 then 1 (`negroni_wlan_mhi.c:347-348`). Low risk: with wake
  held at 1 the device should stay in M0 [I].
- docs/wifi-plan.md "Status (2026-10-25)" and its stage table are stale; README-wifi.md is the current state.
- Cold-boot calibration is **not required** on the ath11k path: `wcn6855 hw2.0/2.1` have
  `.coldboot_cal_mm = false`, `.coldboot_cal_ftm = false` (`core.c:444-446`, `:536-538`), so
  `ath11k_qmi_driver_event_work` goes straight from FW_INIT_DONE to `ath11k_core_qmi_firmware_ready`
  (`qmi.c:3260-3283`). cnss2 does it because the DT says `qcom,wlan-cbc-enabled` (`main.c:3515-3517`, start at
  `:3239-3241` when user space writes `fs_ready`) and then powers the chip down and up again (`main.c:2038-2045`).
  Without it the firmware calibrates in mission mode (HOST_CAP `cal_done = 0`, `negroni_wlan_qmi.c:818`) [I:
  slower first scan, no other known effect].

## 2. Deviations that can bite

1. **All chip addresses are above 4 GiB** [V]. XNU RAM starts at 0x840000000 (notes.md:1263); the pool, the
   IPCR buffers, the firmware segments and the m3 buffer are physical addresses there. Android gives this chip SMMU
   IOVAs 0xa0000000-0xb0000000 (`live.dts:20856`, `pci.c:5503-5506`), its CMA `cnss_wlan_region` is limited to
   0..0xffffffff (`live.dts:326-332`); Linux ath11k gives it 32-bit coherent addresses (`pci.c:24`,
   `qmi.c:2012`, `:2545`). The MHI registers and the QMI `mem_seg.addr` are 64-bit fields, so the protocol
   allows it, but no one has shown the QCA6490 firmware (SBL, AMSS DMA engines, m3) uses bits 32-35 [I]. The
   symptom would be `BHI SBL` time-out or error at step 8, or SYSERR after RESPOND_MEM. Mitigation options:
   (a) carve a <4 GiB window: none exists in this XNU's RAM map [V notes.md:1263]; (b) program an apps-SMMU S1
   context for stream 0x1c01 that maps 0xa0000000+ to the pool (what Android does; needs the hypervisor to let
   us write a context bank: `qcom,skip-init`, `handoff-smrs` `live.dts:15352-15360` [I]); (c) try it as is and
   read the heartbeat lines.
2. **No SMMU translation, bypass assumed.** Step 6 only proves that stream 0x1c01 will not fault (SMR scan,
   USFCFG/CLIENTPD) and stops when EXIDENABLE is set (`negroni_wlan.c:530-534`). It does not know whether the
   hypervisor emulates the global space (README-wifi.md says Gunyah does [I]). `negroniwlan_smmu=2` writes an SMR;
   the owner must approve it.
3. **No cold-boot calibration**: fine for ath11k-class firmware (section 0), but HOST_CAP `cal_done = 0` and the
   firmware will calibrate at mission-mode start; Android's `use-nv-mac` + DMS MAC (`main.c:756`
   `cnss_setup_dms_mac`) has no counterpart; the MAC must come from WMI [I].
4. **Single kernel thread, busy polling**: every wait is `delay(1000)` in a loop (`negroni_wlan_mhi.c:103`,
   `:429`, `:459`, `:502`, `:581`; `negroni_wlan_qrtr.c:357`, `:381`; `negroni_wlan_qmi.c:525`). XNU `delay()`
   spins; the thread burns one core during the whole boot (up to 10 s per wait x ~20 waits) [V code, I cost].
   After level 6 the thread exits and **nobody polls the event rings any more** (`negroni_wlan.c:847-855`): later
   indications (CAL_DONE, memory requests) and M1 transitions are never consumed; the chip keeps DMA into the RX
   buffers (16 x 32 KiB) until ring 21 is empty, then stalls [I]. Harmless for the test, wrong for a driver.
5. **HOST_CAP differences vs the phone's Android** [V]: feature_list lacks DRV (section 0); no `gpios`
   (WSA GPIO 56 for project 20847, `qmi.c:258-331`); no `wake_msi`; `host_build_type` 2 assumed [I];
   `fw_ready_enable` added (ath11k does, cnss2 does not). None is known to block FW_INIT_DONE [I]; the WSA gpio is
   the first thing to add if the firmware refuses or never answers.
6. **M1 handling** differs from Linux (section 0); with wake held at 1 M1 should not occur [I].
7. **No SoC reset before MHI**: ath11k does `ath11k_pci_sw_reset(power_on)` (LTSSM enable, clear interrupts,
   WLAON power control, L1ss fix, `PCIE_SOC_GLOBAL_RESET`, MHICTRL RESET; `pci.c:380-397`, `:193-225`) and
   **disables ASPM during the download** ("problems switching to AMSS state", `pci.c:828-831`). cnss2 does not do
   the global reset; the DT has no `qcom,set-wlaon-pwr-ctrl` (notes.md:1261). Ours relies on a fresh chip in PBL
   after WLAN_EN (checked at step 7). ASPM state of the two ends is not read or forced off [V code]. Add a log of
   LNKCTL[1:0] of the root port and the endpoint at step 1, and clear them [I cheap].
8. **UEFI/XBL/ABL-left state assumed**: PCIe LDOs (pm8350 L5/L6 via `vreg-0p9/1p8`, `live.dts:20800-20801`)
   not voted, no interconnect (BCM) vote for PCIe->DDR (`live.dts:13872-13873`), GCC written directly (slop 0120),
   the PHY table of 0120 differs from the vendor DT in 3 RX values (README-wifi.md 0262 section [I]). The link came
   up Gen2 x1 on the first try, so the link-level part is proven [V]; the DMA/bandwidth part is not.
9. **MHI window = 0..2^36** instead of the exact buffers (`negroni_wlan_mhi.c:194-197`): any bad pointer the
   firmware produces hits RAM. cnss2 without SMMU does the same (`pci.c:5509-5510`) [V].
10. **Firmware area layout** changed after 0261 was written: the area now carries the BT pack too (199 files,
    notes.md:1834); the header allows 256 entries, so 0261 still parses it [V `negroni_wlan.c:92`, `:662-663`].

## 4. Risks for the queued test (`negroniwlan=6`, image `out/ios16-wlan6`)

1. **The firmware area is not on the phone** [V plan.md:244]. Level 2 then stops at step 5 ("no firmware area
   header") before any DMA. The test proves nothing beyond step 4 unless the area is written first (owner
   approval, `scripts/fw/write-areas.sh CONFIRM=yes` or `AREAS=1 root-simg.sh`, notes.md:1604-1621).
2. **Battery**: the only earlier attempt browned out at 16 % (notes.md:1322-1331). The phone drains and does
   not charge under our kernel; charge above 50 % first.
3. **First chip DMA from an address above 4 GiB** (section 2.1) and the **apps SMMU stream** (2.2): the symptoms
   are the same (BHI SBL heartbeat lines with status unchanged, then "not done in 10000 ms", or a silent
   restart). Step 6 lines (`GCC ... vote`, `apps SMMU sCR0 ...`, `stream 0x1c01 ...`) are the first thing to read.
   A restart during the SBL download comes back to fastboot by itself only with `negronipanic=30
   negronipanicreason=2` (the image has them [V plan.md:65]).
4. **Time**: up to ~20 waits of 10 s (`negroniwlan_to` default) plus a 10 s minimum at step 24; a wedged chip
   costs about 3 minutes of one spinning core before `WLAN STOP N` shows [I]. iOS keeps booting meanwhile
   (own thread) [V `negroni_wlan.c:857-877`].
5. **Contiguous allocations after boot**: REQUEST_MEM asks for a few MiB per segment (ath11k: first ~4 MiB block,
   then smaller, `qmi.c:1989-2020`); `kmem_alloc_contig` of that size late in boot may fail; 0266 then answers 0
   segments once (`negroni_wlan_qmi.c:673-682`). A second failure stops at step 20 with "no contiguous memory".
6. **Chip left running after level 6** (section 2.4): the RX ring drains and the chip stalls or raises SYSERR
   later; the badge stays `WLAN OK 6`. No effect on iOS expected [I]. A reboot powers the chip off? No: WLAN_EN
   stays high and the rails stay voted until the next cold boot; the next test must see EE 0 at step 7 or it stops
   ("not in PBL") [V `negroni_wlan.c:702-705`]. The survey's PERST/WLAN_EN cycle at steps 6/8 resets the chip
   on every boot [V `0262:283-286`, I that this is a full chip reset].
7. **QMI refusals** are printed with result/error (`negroni_wlan_qmi.c:571-577`). The first suspects on a refusal
   or a missing FW_INIT_DONE: the WSA `gpios` entry, the DRV feature bit, `host_build_type` (section 2.5).
8. **Unverified assumption**: HELLO goes to node 0xffffffff first (`negroni_wlan_qrtr.c:338`); the chip's name
   service must answer with NEW_SERVER for service 0x45 version 1 within 10 s. If only HELLO arrives, step 17
   times out with "(N other servers seen)"; then try an explicit lookup packet or wait longer (`negroniwlan_to`).
9. **No change to phone-safety rules**: the test writes `boot_a` (image) and userdata (area) only; `negroniwlan_smmu`
   stays 1 (no SMMU write) unless the owner approves 2.
