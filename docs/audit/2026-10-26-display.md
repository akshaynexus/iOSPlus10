# Display stack audit: our patches against the Android display driver (2026-10-26)

Scope: patches/xnu 0231, 0234, 0250, 0251/0258/0275, 0252-0254, 0256/0267, 0257, 0259; the READMEs
(README-gpu-kernel.md sections 8-18, README-brightness.md, README-reboot.md "0258"); docs/display-refresh-plan.md;
docs/notes.md section 15. Reference: `out/src/op-modules/vendor/qcom/opensource/display-drivers` (msm/sde, msm/dsi,
oplus), `out/live.dts` (panel node line 35551, timing fhd_sdc_120 at 35640), the Mu panel XML
`external/Mu-Silicium-negroni/Binaries/negroni/RawFiles/Panel_samsung_amb670yf08_1440_3216_dsc_cmd.xml`.
Read-only audit; no build, no phone. [V] = read in the named file at the named line; [I] = inferred, not read or
not tested. "Android file:line" = the display-drivers tree above.

Short form of the result:

- Done and matched to the Android source: the DSI command FIFO path (0250), the DBV byte order (0250), the panel
  off/on DCS sequence and its waits (0258), the TE counter read (0259), the auto-refresh divider (0259), the min-fps
  DCS and the 60/90/120 timing-switch sets as bytes (0259), the CoreAnimation 120 Hz quantum (0253).
- Done but not how Android does it: frame transfer (we never kick the CTL, the UEFI auto-refresh scans a single
  buffer every TE), the vsync source (a timer that samples a counter, not the rd_ptr interrupt), the DCS mode
  (LP for sets Android sends in HS), the clocks and votes (none: we live on what the UEFI left on).
- Missing: double buffering of the scanned buffer, DSI reads (ESD, panel ID), DPU/DSI power collapse, ULPS, HBM and
  the dimming command, AOD/LP1, any DPU plane work (scaling, rotation, DSC reprogramming).
- Not booted at all: 0234, 0259, 0267/0286, 0275 (the owner's last log is kernel 074105 = 0231..0259 without
  `negronifb_te`/`negronifb_vrr`).

## 2. Deviations from the original driver that can bite

1. **Single buffer + auto-refresh, the copy races the scan [V].** Android latches a new base address per frame (CTL flush)
   and never writes the buffer the DPU fetches. We memcpy/blit into the only scanned buffer while the engine
   fetches it on every TE (README-gpu-kernel.md:884-900 explains the top-left glitch this way). 0267 removes the
   in-place read-modify-write but not the race. 0259 `negronifb_te=1` reduces it by phase only. Fix = a second
   panel-size buffer in the splash region + the 0234 base flip (SSPP_SRC0_ADDR + CTL_FLUSH) after the copy's fence,
   as README-gpu-kernel.md:954-958 proposes.
2. **CTL_FLUSH without the Android autorefresh disable sequence (0234) [V].** 0234 writes CTL_FLUSH while auto-refresh
   is on. Android's `trigger_start` never issues CTL_START under auto-refresh (sde_encoder_phys_cmd.c:2169-2175) and
   disables auto-refresh before any real commit (`_sde_encoder_phys_disable_autorefresh` :2129-2154, two polling
   sequences). Whether a flush alone (no CTL_START) latches the new SSPP address at the next auto-refresh frame is
   not in the source; 0234 detects "not taken" after 100 ms and falls back (0234:391-427). Risk: a flush that
   latches mid-frame (tearing) or never (fallback, harmless). Not booted.
3. **LP vs HS DCS [V].** live.dts states: brightness LP (35579), status read LP (35595); timing switch, qsync min-fps,
   HBM, LP1/nolp all `dsi_hs_mode` (35650-35651, 35693-35699). 0250 sends everything LP by default; 0259 sends mode 2
   (timing sets) HS but mode 1 (min-fps, `BD[0x14]`) LP unless `negronifb_vrr_hs=1` (0259:610). The off-command state
   is not set for this panel node (grep of 35551-35640: only the status-command state), so Android's default is LP
   (dsi_panel.c:2679-2680 `!state || "dsi_lp_mode"` -> LP): 0258's LP 0x28/0x10 matches. An LP long write of 34 bytes
   (the C5 packet of the switch sets) takes ~30 us at 10 Mbit/s: fine in itself; the risk is a DDIC that expects HS
   for the Samsung-key sequences (F0 5A 5A ... F7 0F), unknown [I]. Recommendation: `negronifb_vrr_hs=1` for mode 1
   too, to match the DT.
4. **The MDP-busy wait makes every packet slow [V].** 0250 waits up to 20 ms for STATUS bit 2 (MDP stream idle) before
   each packet, and 0259's sets are 62 packets each (0259:190-379): 62 x (wait + 25 ms poll budget) = the "100-300 ms
   per switch" of display-refresh-plan.md:175. Android does not wait for MDP idle per command (only dsi_display.c:8959
   in the dynamic-clock path); the controller queues the DMA behind the stream. Android also batches packets with the
   `last` flag (dsi_ctrl.c:1698-1699, 0x40 in the set headers = batch) into one DMA from memory. Our FIFO path cannot
   batch beyond 64 bytes, so a memory-fetch path (DSI_CTRL_CMD_FETCH_MEMORY, `dsi_ctrl_hw_cmn_kickoff_command`
   dsi_ctrl_hw_cmn.c:870) would be the Android way for the long sets. Risk now: a 300 ms switch during which the tick
   keeps running (fine) and the display-off fade waits up to 500 ms (0259:482-497).
5. **No DPU/DSI clock, GDSC or bus votes; everything is UEFI-left state [V].** Android votes DSI clocks and the command
   engine per command (dsi_ctrl.c:3581-3604) and collapses MDSS after 58 ms idle (sde_encoder.h:55). We assume the
   UEFI left the DSI0 command engine, the byte/pixel clocks, the MDSS GDSC and the bus at a working level and never
   touch them. Observed OK for days of boots (brightness works, 0250 logs), but: (a) if a future patch (RPMh, clock
   manager, Wi-Fi/GPU GCC work) drops a shared vote, the DSI0 DMA stalls (0250's "DSI0 commands disabled after 3
   failures" would be the symptom); (b) no power saving while idle.
6. **The tearcheck `vsync_count` stays at the 120 Hz value after a 60/90 Hz switch (0259 mode 2) [V code, I effect].**
   Android re-programs it (sde_encoder_phys_cmd.c:1240-1246). With TE-pin mode and start_pos = init the write still
   starts at the TE; the line counter only models the panel scan for the sync threshold. 0259's TE phase arithmetic
   (`fTeLineNs` from the boot-time `vsync_count`) stays correct because it measures the TE period itself; the sync
   window is what may be off.
7. **Mode 1 hold with frames still arriving [I].** Android sends `BD[0x14] = N` only in `OPLUS_ADFR_IDLE_ON` with no
   commits (oplus_adfr.c:2900-2915) and clamps to 20 Hz otherwise (:2478-2485). We send N = 0x0b (10 Hz) while the
   auto-refresh divider still delivers one frame per 12 TEs. Unknown panel reaction (flicker or a rejected write).
   display-refresh-plan.md:177-178 says the same. Mode 3 (divider only) is the Android-safe subset.
8. **No ESD, no reads [V].** Section 1. A dead panel = black until reboot; no way to read 0x0A/0x0D/serial.
9. **Sleep-out without re-init [I].** 0258 wakes with 0x11/0x29 only. The panel's register state (PPS, 60/BD/B9 blocks,
   53 28, 2A/2B window) must survive sleep-in. Samsung DDICs keep them [I, common behaviour, not in the source]. If a
   wake ever shows a wrong mode (e.g. 60 Hz TE after a 0259 mode 2 idle period followed by sleep), the cause is here:
   0259's `vrrWakeLocked` on RequestPowerChange (0259:956) sends the 120 Hz set only when `ready`
   (0259:858 `wantIdle && !ready`; the wake path `if (ready)` 0259:877), so a sleep during idle
   may leave the panel in the 60 Hz state until the next swap after wake [I: needs a trace].
10. **DCS from a thread call during the display-off DCS (0258 + 0259) [V].** Both go through `negroni_dsi_lock`, so they
    serialise; 0259 adds the 60-tick wait so the sleep DCS does not land inside a set (0259:482-497). Residual: the key
    lock `F0 A5 A5` best-effort after a failed set (0259:924-925) is sent with the panel in an unknown page state.
11. **0275's black pass on the vsync work loop [V].** 1080x2412x4 bytes of 8-byte stores to write-combined memory:
    ~3 ms by the patch's estimate (0275 header), not measured. One late tick at most.
12. **0231's GPU blit does not check sy + h against the source height** (README-gpu-kernel.md:961, pre-existing).

## 3. What remains, by value for "smooth 120 Hz UI + low power"

1. **Panel double buffer with a DPU base flip after the copy's fence** (removes the copy/scan race, item 2.1).
   Android reference: `sde_hw_sspp_setup_sourceaddress` / the per-commit flush (`sde_hw_ctl_trigger_flush_v1`
   sde_hw_ctl.c:685-711, SSPP bit table :78-79: VIG0 = bit 0, CTL = bit 17) and the latch at the frame boundary.
   Needs the 0234 DPU probe lines from one boot first (never captured, README-gpu-kernel.md:956-958).
2. **Present on render completion with a TE-locked tick** (0259 `negronifb_te=1` + a tick that copies as soon as the
   fence is done, up to 8.3 ms earlier). Android: the rd_ptr interrupt as the vsync (sde_encoder_phys_cmd.c:313-424)
   and `wait_for_idle` (:878) before the next kick. Long form: the MDSS IRQ (GIC SPI 83) with the tear irq block
   +0x800 bits RD_PTR/WR_PTR (sde_hw_interrupts.c, display-refresh-plan.md:49-51) instead of counter sampling.
3. **Zero-copy (0234) boot test.** The flip code exists; one boot with `negronifb_zerocopy=1` and `negronifb_noconsole=1`
   answers whether CTL_FLUSH latches under auto-refresh (item 2.2). If it does, item 1 is the same code with the
   panel memory as a second slot.
4. **Android-style idle: no transfer, then the ADFR min-fps hold** (replaces mode 1's "hold + divider"). Needs
   auto-refresh off + software CTL_START per frame (`sde_encoder_phys_cmd_trigger_start` :2161-2182,
   `_sde_encoder_autorefresh_disable_seq1/2` :2015-2127) and the pp_done/wr_ptr handling (:234-286, :424-486). Then
   idle = nothing on the DSI link, and `oplus_adfr_handle_idle_mode` :2836-2947 as written (enter at idle, exit value
   `minfps_exidle` 0x05 on the next frame).
5. **DPU/DSI clock and bus votes, power collapse while idle.** `_sde_encoder_rc_idle` sde_encoder.c:2207-2262 and
   `_sde_encoder_resource_control_helper` :1777+ (DSI clocks off, `pm_runtime_put_sync` for the MDSS GDSC, bus release
   `sde_core_perf_crtc_release_bw` sde_core_perf.c:786). Our RPMh/clock code (0240/negroni_rpmh.c, notes.md) votes
   rails on only; a DPU vote path does not exist. Largest power item; also the riskiest (a wrong collapse = black
   screen until reboot).
6. **DSI read path + ESD check** (`dsi_ctrl_hw_cmn_clear_rdbk_reg` dsi_ctrl_hw_cmn.c:1037-1043, `get_cmd_read_data`,
   `dsi_display_status_reg_read` dsi_display.c:1003-1065, expected 0x9d/0x9f every 5 s). Gives recovery (re-init =
   item 7) and the panel serial number.
7. **Full panel re-init path** (reset GPIO 3 sequence live.dts 35616, rails l12/l13, the on-command incl. PPS,
   `dsi_panel_enable` dsi_panel.c:5708-5813). Needed by 6 and by any rail-cycle sleep (`negronifb_sleep=2`).
8. **Memory-fetch DMA with batching for the long sets** (dsi_ctrl.c:1701-1731, `kickoff_command` dsi_ctrl_hw_cmn.c:870)
   and HS mode where the DT says so (item 2.3/2.4): turns a 62-packet switch from ~100-300 ms into one DMA.
9. **Tearcheck re-config on a rate switch** (sde_encoder_phys_cmd.c:1240-1246, `sde_hw_intf_setup_te_config`
   sde_hw_intf.c:622-666) for 0259 mode 2.
10. **HBM / 0x53 dimming control** (oplus_bl.c:205-305, live.dts 35713-35716). Comfort item; low risk.
11. **AOD / LP1** (`dsi_panel_set_lp1` dsi_panel.c:5192, live.dts 35712 `28; F0 5A 5A; 53 24; F0 A5 A5`): only if iOS
    always-on is wanted; not for iOS 16 on this device.

## 4. Open risks for the queued phone test (`out/ios16-everything`, `negronifb_te=1 negronifb_vrr=1`)

- `negronifb_te=1` is read-only except `INTF_VSYNC_TIMESTAMP_CTRL` with `=2` (0259:592): no panel risk. Watch the
  boot line `NEGRONI FB TE: INTF_1 tear_en 1 sync_cfg 0x..` : `te pin 1`, `vsync_count 66`, `init 2412`,
  `autorefresh 0x80000001` are the expected UEFI values (display-refresh-plan.md:146-149). If `vsync_count` is not 66,
  the 19.2 MHz assumption or the UEFI's configuration differs: the phase target scales, the lock still works
  (display-refresh-plan.md:179-180). `te/s 0` or `no sample` high = the counter is not in TE-pin mode: `negronifb_te=0`.
- `negronifb_vrr=1` (mode 1) is the mode with the most unknowns (items 2.3, 2.7): the LP min-fps write, the hold with
  frames arriving. Failure modes: (a) a rejected set -> `idle switch failed ... VRR off` (safe, VRR off for the boot,
  0259:911-927); (b) the panel accepts and flickers at 10 Hz on the lock screen (visual; `negronifb_vrr=3` or `=2`
  next); (c) a half-sent set leaves the Samsung key open; the best-effort `F0 A5 A5` closes it (0259:924-925); (d) the
  3-failure DSI shutdown of 0250 is reached only if two more DCS fail after the VRR is off (the brightness writes).
  Recovery for every case: reboot with `negronifb_vrr=0` (the config args do not carry the flag, plan:173-174).
- Interaction with 0258/0275 display off: the fade waits <= 500 ms for a running set (0259:482-497), then sends the
  sleep DCS anyway with the log line `display off: VRR set still running after N ticks`; a set that is still inside
  the Samsung key at that point is item 2.10. Expect the normal `display off (fade N ms, DCS sleep ok)` within 25 ms
  (0275).
- Wake after an idle period + sleep (item 2.9): on RequestPowerChange(1) `vrrWakeLocked` resets the divider and
  queues the thread call; the DCS runs when the thread call finds `ready` true (backlight `fDisplayOn`), so the
  order 0x11/0x29 (0258, backlight work loop) vs `BD[0x14]=00` (0259 thread call) is not fixed [V code, I effect].
  Both are LP single writes behind the same lock; a `BD` write to a sleeping panel is ignored by the DDIC [I]. If the
  panel wakes at 10 Hz, the swap after wake sends the exit set again (0259 `swap()` -> `vrrWakeLocked`, 0259:945)
  only if the state is not already `active`: it IS active after the first (ignored) exit set, so the panel could stay
  at 10 Hz until the next idle/exit cycle. Check the first seconds after a wake for a 10 Hz feel [I].
- The stats lines for TE/VRR need `negronifb_stats` != 0 (default 1, display-refresh-plan.md:150); `out/ios16-everything`'s
  exact boot-args were not read in this audit [I].
- Not display, but in the same image: the 0267/0286 defaults (`negronifb_notifylate=1`, `negronifb_clockcopy=1`,
  `negronigpu_uifloor=9`) are also untested; a regression in the status-bar strip or in presents/s is theirs, not
  0259's. A/B: `negronifb_clockcopy=0`, `negronigpu_uifloor=0`.
- Zero-copy (0234) is off unless `negronifb_zerocopy=1` is in the args; the DPU probe runs read-only every boot
  (`negronifb_dpuprobe=0` skips it) and maps 528 KiB of MDSS registers from kernel_map (0234:40-43); a probe line
  `NEGRONI FB: DPU VIG0 addr 0xb8000000 ...` is the first data point for section 3 item 1.
